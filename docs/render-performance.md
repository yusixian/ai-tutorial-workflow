# 渲染提速

## 先找耗时在哪里

Remotion 逐帧绘制画面，再交给 ffmpeg 编码。模糊、大阴影、大尺寸图片和复杂动画都会增加成本。

用自己的工程选一个有代表性的短场景测试，记录画面复杂度、并发设置和资源占用，一次只改一个参数。这里不保留原项目的机器型号、内存配置、成片规模或渲染耗时。

## 减少重复渲染

1. **只渲改过的集。** 渲染脚本接受集名，未变的成片继续复用。
2. **先用小样确认。** 修改画面时先看关键帧和短片段，确认后再全量渲。
3. **复杂静态画面预先导出。** 封面展示等不需要逐帧变化的内容，提前生成图片，再放入场景。
4. **合集复用分集。** 模板的 `pnpm compilation` 直接拼接 finalize 后的分集，不重新绘制画面。

## 公共进度层

如果需要给合集增加公共进度层，可以单独渲染透明层，再用 ffmpeg 叠加到拼接好的视频。时间轴不变时，这一层也可以缓存。

这属于扩展方案，模板没有提供完整的合集进度层脚本。实施时注意：

- 透明视频的编码与合成方式是否兼容。
- 分集自己的进度条在过场时是否仍然可见，是否需要局部真实渲染补齐。
- 叠加后帧数、拼接边界、色彩和音画同步是否正确。
- 降低进度层的更新频率前，先检查实际移动幅度与播放效果。

总长度一致不代表每一帧一致，改完需要看片。

## 并发与截图格式

并发增加后，画面计算或内存可能先达到瓶颈。出现浏览器崩溃或性能下降时，降低并发，避免同时运行占资源的本地模型。

截图格式变化也要检查输出兼容性。模板使用 PNG 帧、BT.709 和 `yuv420p`（见 `video/remotion.config.ts`）；改成其他格式时，核对色彩范围和播放器表现。

没有改善的设置就撤回，保留测试记录，不把别人机器上的成绩当成自己的预期。

## 稳定性

- 一个工作区同时只运行一个正式渲染，避免争用缓存和输出目录。
- 渲染前确认可用资源，本地模型与渲染按任务需要错开。
- 先渲到暂存位置，归一和检查通过后再替换正式文件，旧版保留备份。
- 偶发崩溃与持续失败分开处理，持续失败先看日志和资源占用。

## 交付检查

在 `video/` 下运行：

```sh
pnpm finalize ep1 ep2     # 两遍 loudnorm，视频流直接复制
pnpm delivery-check       # 帧数、编码、色彩、音频、音画时长差、完整解码
```

检查通过后，人再从头看一遍、听一遍。文件能解码与教学效果好，需要分别确认。

## 工程兼容性

- TypeScript 与打包工具的兼容处理在 `video/webpack-override.ts`，调整依赖版本后检查 JSX 输出与渲染。
- 渲染机器需要安装所用字体。模板使用系统字体，要在不同机器上得到一致画面，先准备相同的字体。
- 在线字体会增加渲染时的网络依赖，正式制作时可以改用有授权的本地字体文件。
